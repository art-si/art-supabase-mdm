# MDM views

MDM 维护跨业务域主数据的统一目录、质量治理、四眼变更、黄金记录和可靠事件交付。来源应用仍是业务主档的权威写模型；治理中心只通过数据库授权 RPC 生成审批记录和 Outbox 指令，由来源适配器幂等执行，避免双写。

## 配件加工清单

工程主数据下的“配件加工清单”使用 `mdm-accessory-processing` 私有存储桶。统一 DOCX 模板、PNG/JPG/WebP、PDF 和 DOCX 原件可上传；浏览器将前三页栅格化供识别，文件上限为 20 MB。识别返回物理表格行及长度/数量组合，系统将每个组合展开为独立加工件，并把该行草图裁剪到单独的租户文件路径。看不清的草图需人工补传。

普通已授权用户可查看租户范围内的清单并使用识别预览；保存草稿、修改业务数据及生成单据只允许平台超级管理员。该限制同时存在于页面按钮、角色菜单、`mdm_save_accessory_processing_draft` / `mdm_generate_accessory_processing` RPC 和表 RLS。识别接口要求 `MdmAccessoryProcessing:Recognize`，仅接受调用者上传到该私有桶 `page` 目录的短时签名图片地址；`mdm_validate_accessory_ocr_pages` 只授予服务角色执行。

识别结果按原表行分组，行内每种长度仍是独立加工件。各行可折叠，摘要显示名称、加工件数和长度组合；默认只展开带行级核对提示的分组，并提供全部展开/收起。普通用户以只读摘要查看，平台超级管理员展开单件校对。页面把“我的识别记录”和“已保存清单”分开：前者读取当前登录者在当前租户范围内的 `ai_artifact_review` 审计记录，刷新后可打开识别文字，并通过审计记录的页图索引在私有桶内重新签发原件和逐件草图地址；后者仅读取已由平台超级管理员保存的 `mdm_accessory_processing_list` 业务数据。文件暂时无法恢复时仍显示识别文字并提示预览失败，不把预览当成已保存的业务清单。2026-09-28 核对：目标库有 1 条 11 件的配件识别审计记录、0 条已保存业务清单，审计记录所属上传组保留原件和 11 张独立草图。

生成 RPC 在一个数据库事务内按项目名称唯一匹配现有项目，或在指定客户后创建项目；再建立独立项目父物料、生产用途 BOM、每件子物料和逐件草稿加工单。物料编码 `ACC-<加工件 ID 的完整 32 位十六进制值>`、项目编码 `PJACC<清单 ID 的完整 32 位十六进制值>`、加工单号 `JG-<加工件 ID 的完整 32 位十六进制值>` 具有稳定来源且不会截断碰撞。每件草图路径保留在加工件记录和对应物料说明中；生成后清单只读，重复调用返回已生成结果。物料分类和“件”计量单位必须在目标租户有效。

验证记录：通过事务回滚样例确认同一原表行的 2.7 m 和 4.8 m 被拆为 2 个加工件、2 个不同物料、2 个 BOM 子项和 2 张加工单；普通用户身份调用草稿 RPC 返回 `42501`，专用图片校验 RPC 不允许普通角色执行。`ai-accessory-processing-contract.test.ts` 覆盖拆分及无效行；MDM 类型检查、构建、ESLint 和 UI 审计通过。生产构建的桌面及 390 px 页面通过浏览器检查，无横向溢出；DOCX 模板在浏览器中完成原件、识别页和两张独立草图的上传链路。

2026-09-28 模型故障核查：两次三页 PDF 识别先遇到 OpenAI 通道 401，随后 NVIDIA 的 `meta/llama-3.2-90b-vision-instruct` 在约 120 秒超时。平台特性配置改用 `meta/muse-glimmer-30b` 视觉模型，不再配置 90B 回退；识别函数优先使用配置指定的 NVIDIA 通道，并为该模型使用低推理强度。以用户提供的中文雨篷样张进行真实 NVIDIA API 测试：单页完整 JSON 在约 24 秒返回并通过加工件契约验证，三图完整 JSON 在约 35 秒返回并识别出 6 个有内容行，其中第一行的 2.7 m 和 4.8 m 保持为两个加工件。模型未给出可信草图边界时返回 `null`，仍需在生成前人工补图及核对；实际三页业务 PDF 的端到端复测需使用登录会话完成。
